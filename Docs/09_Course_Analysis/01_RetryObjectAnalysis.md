# G-UC-06 重试：用例与局部对象分析

基线：[COURSE-20261018-R1](README.md)。重试起点、跳过开场和旧局隔离沿用原需求；恢复失败出口由本人于 2026-10-18 确认，见 `DEC-01`。下列对象职责、关系与 BCE 是本轮分析工作稿，尚无本人/同伴模型审查通过记录，也没有据此声明游戏已实现或运行验收通过。

本页保存 G-UC-06 的详细事件流与局部分析，供课程 Word 纳入同版本结果；玩家体验规则仍以[第一关流程](../02_Design_Doc/GDD/01_GameFlow.md)为唯一来源，具体测试步骤和结果在[开发检查清单](../06_Test_Doc/01_VerificationMatrix.md)。

`Playthrough` 表示从开始或重试进入的一轮游玩；`BossEncounter` 表示该轮游玩中的指定 Boss 业务遭遇；`CombatResult` 表示该轮的终局事实。它们是分析概念，不要求创建同名 UE 类。一个业务遭遇可能按 RL 契约包含多个策略/遥测记录段，换策略不能冒充重试或新业务遭遇。

本页不分析继续游戏、持久检查点、通用背包或完整资产加载实现。结果页退出和返回菜单各有独立用例，只有重试失败后转交这些出口时才在这里引用。

<a id="g-uc-06"></a>
## 2 G-UC-06 详细规格

| 项目 | 规格 |
| --- | --- |
| 目标 | 结束旧局影响，以干净状态恢复到本关初始可操作点 |
| 主参与者 | 玩家 |
| 触发 | 玩家在可操作的结算界面点击重试 |
| 前置 | 旧游玩已有终局结果；当前没有尚未完成的重试或返回菜单操作 |
| 需求/规则 | GAME-FR06，BR-GAME-02/03/04；错误出口关联 GAME-FR07/08 和 NFR-GAME-01 |
| 成功终点 | 新游玩处于可操作的探索起点，尚未建立新 Boss 遭遇 |

### 基本流

| 步骤 | 参与者动作与系统响应 | 主要职责 |
| --- | --- | --- |
| 1 | 玩家点击重试。系统检查当前结果及转换状态，接受一次恢复请求并屏蔽重复提交，保持战斗输入关闭。 | 结果交互边界、重试控制 |
| 2 | 系统结束旧游玩的运行影响，停止旧遭遇决策/记录段，使旧请求与回调失效；清理委托、UI 和单局状态。旧结果可保留归档，不再用于改变当前局。 | Playthrough、BossEncounter、恢复边界 |
| 3 | 系统恢复关卡初始角色/敌人、生命、能力、冷却、镜头、UI 和输入配置，准备具有新身份的游玩；跳过营火菜单与开场。恢复过程中尚不开放战斗。 | 恢复边界、候选新 Playthrough |
| 4 | 系统核对恢复就绪，将候选新游玩设为当前游玩，恢复探索输入并显示适用 HUD；清除恢复忙碌状态。 | 重试控制、新 Playthrough、交互边界 |

步骤4完成即结束本用例。玩家随后按 G-UC-02 探索，按 G-UC-03 入场；Boss 交接完成后才建立新遭遇与初始策略记录。再次走到 Boss 不属于重试成功前必须完成的工作。

### 步骤绑定的扩展

| 扩展 | 条件与系统响应 | 落点 |
| --- | --- | --- |
| 1a | 重试/返回过程已进行中又点击：忽略重复输入，不建立第二个恢复操作或候选游玩。 | 继续已有步骤2–4；不新开用例 |
| 1b | 点击来自失效结果界面或旧游玩：不接受该操作，不影响当前合法游玩。 | 终止这次无效请求 |
| 2a | 旧策略/同伴响应或伤害在清理期间或之后返回：按游玩、遭遇、请求身份和当前阶段拒绝，不改变新局或当前恢复状态。 | 继续当前步骤 |
| 3a / 4a | 关卡恢复或就绪检查失败：保持禁战斗，报告未恢复成功，允许重新尝试或返回菜单；不将半恢复状态设为当前可玩游玩。 | 玩家重试则重新进入步骤2；选择菜单则转 G-UC-07 |
| 3b | 返回菜单也恢复失败：保持禁战斗并给出重新尝试或退出。 | 重新尝试菜单恢复，或转 G-UC-08 |
| 3c / 4b | 旧恢复操作的迟到完成事件到达：核对恢复操作身份，不能激活已被替代的候选游玩。 | 继续当前有效恢复，或维持当前合法状态 |

恢复失败和菜单失败的出口按 `DEC-01` 作为需求目标。这里没有承诺事务回滚：部分清理可能已经完成，重新尝试必须从当前实际状态安全恢复，不能谎报旧世界完全不变。

### 保证与验收入口

成功保证：新旧游玩身份不同；当前玩家处于 BR-GAME-03 定义的起点与控制状态；旧局影响被隔离；尚无新 Boss 遭遇或其决策记录。

失败最小保证：不开放部分恢复的战斗状态，不接受旧局伤害或指令，不重复使用旧终局；界面如实报告失败并提供合法恢复/退出出口。失败不等于恢复成功，也不等于已经通过实际故障测试。

| 检查 ID | 本用例要核对的性质 |
| --- | --- |
| C-08 | 连续两轮重试后返回菜单再开始，体验规则及单局状态一致 |
| C-08a | 重复提交只存在一个有效恢复操作与新游玩 |
| C-08b | 旧策略/同伴响应、伤害或恢复回调不污染当前状态 |
| C-08c | 恢复/菜单失败禁战斗，恢复或退出出口可达 |
| C-08d | 恢复起点时无新遭遇；完成下一次 Boss 入场后才建立 |
| EXIT-03 | 服务离线与恢复失败不会阻塞合法退出 |

步骤、数据与运行结果只在检查清单记录；本页用于说明它们为何验证这个用例。

## 3 候选对象筛选

| 候选 | 处理 | 依据与职责边界 |
| --- | --- | --- |
| Playthrough 本次游玩 | 保留，核心实体 | 有独立身份及进行/结束状态，承担本轮状态合法性；关联终局与可选 Boss 遭遇 |
| BossEncounter Boss 遭遇 | 保留，核心实体 | 区别业务战斗与遥测记录段，约束决策适用身份和停止时机 |
| CombatResult 战斗结果 | 保留，支持性结果对象 | 表达旧局的不可变终局事实；不组织重试，也不需要为了课程新造持久化实体类 |
| RetryCoordinator 重试协调 | 保留为局部 control 职责 | 协调恢复步骤与失败出口，不能代替实体维护全部业务规则 |
| ResultBoundary 结果交互 | 保留为 boundary 职责 | 接收玩家选择、呈现恢复状态/错误；不自行判断 Boss 胜负 |
| LevelRecoveryBoundary 关卡恢复边界 | 保留为 boundary 职责 | 将“恢复并报告就绪/失败”交给外部场景实现；不是把全部游戏规则搬入加载器 |
| RetryRequest 独立业务实体 | 不单独保留 | 本样例用一次请求/恢复操作标识即可解释去重，不需要长期有身份的请求对象 |
| RecoveryState 独立实体 | 暂并入协调状态 | 尚无独立业务生命周期或长期记录需求；未来如需跨启动恢复再重新评估 |
| USaveGame / Widget / GameMode | 不作为本次领域对象 | 属实现选择或技术类；已有映射可用于接线，不能代替本轮业务分析 |

筛选依据是职责与范围，不为凑“删除对象”数量故意制造错误概念。

## 4 CRC 与业务职责

| 对象 | 业务职责（每项可独立解释） | 协作者 | 依据 |
| --- | --- | --- | --- |
| Playthrough | R-PT-01：维护本轮身份及合法运行阶段；R-PT-02：关联一次终局并使已结束游玩不再接受战斗变化 | BossEncounter、CombatResult、RetryCoordinator | GAME-FR05/06，BR-GAME-02/03/04 |
| BossEncounter | R-BE-01：管理指定 Boss 遭遇的建立与终止；R-BE-02：校验决策/执行反馈属于本遭遇及当前可行动阶段 | Playthrough、策略记录、执行反馈、RetryCoordinator | GAME-FR02/06，BR-GAME-01/04，BR-RL-02 |
| CombatResult | R-CR-01：表达本次游玩的终局事实与归属；R-CR-02：提供结算显示和合法后续操作所需的信息 | Playthrough、ResultBoundary | GAME-FR05/06/07/08，BR-GAME-02/07 |

这些职责不是 getter/setter 清单。结果对象可保持不可变，不要求为每项职责增加一个实现方法；协调控制不能直接篡改实体的阶段或绕过拒绝条件。

## 5 不变量与反例

| ID | 必须始终成立的业务约束 | 反例与核对 |
| --- | --- | --- |
| INV-PT-01 | 同一游玩最多一个终局结果；结束后不接受战斗变化，新一轮不能复用旧游玩身份 | 同次死亡生成两个结果，或旧回包改变新局生命；MATCH-01、C-08b |
| INV-BE-01 | 每个遭遇仅属于一个游玩及指定 Boss；未建立或已终止的遭遇不能接受动作影响 | 恢复到起点即建立遭遇，或旧遭遇执行下一局决策；C-08b/d |
| INV-CR-01 | 结果只描述所属游玩的一个终局事实，形成后不能由重复/旧局事件改写 | 旧玩家死亡把新局结果改写，或已确定失败又改胜利；MATCH-01、C-08b |

“失败不进入半恢复战斗”还是协调层的跨对象保证：恢复边界完成并经就绪检查后才激活新游玩。它应由用例控制、实体阶段校验与边界反馈共同实现，不能只靠 UI 禁用按钮。

<a id="relationship-rel-game-01"></a>
## 6 REL-GAME-01：游玩与 Boss 遭遇

本样例选择普通关联，不先假设组合销毁语义。模型范围为一关、一个目标 Boss；未来多 Boss 内容另行修订。

| 方向 | 角色与多重性 | 业务解释 |
| --- | --- | --- |
| Playthrough → BossEncounter | `currentEncounter : 0..1` | 一轮游玩在探索/入场未就绪时没有 Boss 遭遇，进入本关目标战斗后至多一个 |
| BossEncounter → Playthrough | `playthrough : 1` | 每个遭遇唯一归属于建立它的游玩，不能被下一次重试接管 |

这里表达业务归属，不借导航箭头表达执行顺序。入场触发、就绪和创建的时间顺序由 G-UC-03 与游戏状态模型说明。

| 实例/边界情形 | 是否满足关系与约束 |
| --- | --- |
| 重试恢复成功：新游玩位于起点，尚无遭遇 | 满足 `0..1` 的0；若把遭遇端设为1就会误拒绝合法情形 |
| 玩家在探索阶段死亡，有终局结果而无 Boss 遭遇 | 合法；终局归游玩，不强制依附 Boss 遭遇 |
| 完成入场后当前游玩关联一个目标遭遇 | 满足 `0..1` 的1 |
| PPO 故障切 BT，产生新策略记录段 | 仍是原业务遭遇，不能因此新建第二个 BossEncounter |
| 旧遭遇仍作为已结束记录保留，新游玩尚无遭遇 | 合法；归档归属仍是旧游玩，不能当新游玩的 currentEncounter |
| 一条遭遇同时被两次游玩认领，或重复入场建立第二个业务遭遇 | 非法；分别违反反向1和正向至多1，C-08a/b/d验证 |

是否长期保存记录属于归档策略；结束运行对象不等于销毁全部历史。REL-GAME-01不以同局策略记录段数量改变多重性。

<a id="bce"></a>
## 7 BCE 分工与协作消息

| 版型/逻辑职责 | 负责什么 | 不应承担什么 |
| --- | --- | --- |
| boundary：ResultBoundary | 接收重试/恢复选择，显示进行、成功或失败，恢复合适输入焦点 | 判定胜负、绕过实体状态、把错误隐藏成成功 |
| boundary：LevelRecoveryBoundary | 接收恢复上下文，执行场景/角色/界面重建，带恢复操作标识报告就绪或失败 | 自行宣布新业务遭遇开始，替代全部规则检查 |
| control：RetryCoordinator | 受理一次操作，协调旧局失效、恢复、就绪检查和合法出口 | 保存所有实体状态或直接改写终局事实 |
| entity：Playthrough | 保护游玩身份、阶段与终局约束，承认就绪后的新游玩状态 | 操作具体 Widget、HTTP 或地图加载 API |
| entity：BossEncounter | 保护遭遇身份与终止条件，拒绝失效决策/反馈 | 把策略建议当命中或主导菜单/UI |
| 结果对象：CombatResult | 提供所属游玩的终局事实与可显示结果 | 组织重试、加载关卡或维护外部请求 |

### 成功消息清单

1. 玩家 → ResultBoundary → RetryCoordinator：提交当前结果的重试请求。
2. RetryCoordinator → 旧 Playthrough / BossEncounter：验证终局与归属、结束运行影响；请求失效和清理经恢复边界协调。
3. RetryCoordinator → LevelRecoveryBoundary：带新恢复标识和入口方式准备干净游玩；旧游玩仍为已结束。
4. LevelRecoveryBoundary → RetryCoordinator：返回本次恢复就绪及候选新游玩信息。
5. RetryCoordinator → 新 Playthrough：确认满足起点/状态条件后激活探索；→ ResultBoundary：关闭结果/恢复提示并呈现可操作状态。

清单在此结束，没有“创建 BossEncounter”消息；该消息留到后续 G-UC-03 入场交接完成。

### 失败与重复消息清单

- 重复重试请求 → RetryCoordinator：发现当前恢复忙碌，保留原操作，不发第二次恢复命令。
- 旧响应/旧恢复完成 → 接收边界与实体/控制：复核身份、归属和阶段，拒绝其业务影响，不激活已失效候选游玩。
- LevelRecoveryBoundary → RetryCoordinator：恢复失败；控制保持新游玩未激活 → ResultBoundary：显示重试/返回菜单。菜单恢复也失败则显示重试/退出，所选退出交 G-UC-08。

这是职责及消息顺序的分析说明；BCE结构依赖不等于执行时序，也不要求上述职责逐个映射成 UE 新类。A05 游戏类模型与 A08 游戏状态模型表达本页的对象/阶段，A09 RL时序与 A10 NPC时序分别补跨端消息风险。

## 8 追踪与审查状态

完整 FR/NFR/BR—UC—对象—TC/AT 对应见 [02_Traceability](02_Traceability.md)，人工/同伴审查及真实 AI 原始输出见 [03_AIModelingEvidence](03_AIModelingEvidence.md)。本页未替成员填写模型接受结论。

审查至少核对：每个保留对象能反查需求；核心对象两职责与一不变量说得通；REL-GAME-01双向及0/1边界成立；恢复失败不伪装成功；旧回包不改新局；BCE不由万能控制吞掉实体规则。实际发现什么问题据实记录，没有发现错误也应保留检查范围，不凑错误数。
