## 2. 老师的要求分为四个层次

### 2.1 需求本身必须有来源和人工确认

第1课第17页、第2课第34页、第3课第64—65、68、70页共同强调：人确认业务范围、权限、规则和验收，AI只能在该边界内生成或提出待确认问题。

对你们来说，至少要能回答：

- 本版一定交付什么，哪些明确不交付？P0/P1是优先级还是本次必交范围？
- 重试为何回关卡起点、何时建立Episode、什么叫一次终局？
- 哪些错误触发BT回退，回退后如何继续？
- NPC哪些能力被允许，事件如何去重，回执怎样证明实际执行？
- 规则由谁、在哪个版本确认？未决定的内容影响哪些模型和测试？

你们已有分工、范围、P0/P1/P2和资料来源，是良好起点；但“依据现有资料编制”还不能替代每项关键规则的版本与确认记录。未定项应保留，不应让AI猜数值后把它写成既定需求。

### 2.2 模型要解释业务，并保持图表文一致

第2课第31—33页把完整Spec定义为结构化文本、UML多视图、业务约束和验收。各视图必须描述同一组业务事实。第4课第7、52页进一步要求类、属性、操作和关系能反查REQ/BR依据。

因此老师不仅会问“有没有用例图、类图”，还会问：为什么有这个对象？它维护什么状态、负责什么行为？某条关联为什么是1、0..1或0..*？一段异常发生后还有没有合法结果？

你们图7已承认但未修复的技能多重性冲突，在这套要求下比缺少一张装饰性架构图更值得优先处理。

### 2.3 从目标走向对象职责和协作

第4课第14、23、51、54页强调核心对象要承担业务职责、保护不变量；第5课第37—43、54页强调一个用例需要边界、控制、实体之间的合理分工。

这并不要求把每个类画成代码规格。第4课第19页明确说类可以没有操作，第14页也说不要求写满getter/setter。你们图6、图9是概念模型，可以保留这种层次；但若用来满足第4、5课的对象分析任务，还需补一个局部的职责、约束和协作说明。

## 4. 类的版型和用例协作到底要做到什么程度

### 4.1 应说明职责，不应硬套实现架构

第5课第37—40页比单独版型讲义的概述更具体：

| 版型 | 责任 | 在本项目中的候选表达 |
| --- | --- | --- |
| boundary 边界 | 与外部交互、输入输出、格式与结果呈现 | 结果界面、NPC指令入口、策略服务通信边界 |
| control 控制 | 组织一次用例、协调对象及跨对象操作 | 重试流程协调、Boss决策流程协调、指令处理协调 |
| entity 实体 | 业务身份、状态、合法变化与不变量 | 本次游玩、Boss遭遇、关系状态、指令记录 |

这是职责分配的候选，不要求它们与UE的Widget、GameMode、Actor、Component按名称一一对应。边界类并非只能是UI，也可以承担外部接口交互；实体类也不能一律等同数据库表。单独版型讲义中的“持久存储”是简化示例，你们还存在暂态游玩/遭遇对象，应结合第4、5课的身份、状态和职责来分析。

**控制类可以存在。**老师反对的是万能Service吞掉全部规则、把分析类图变成技术目录，而不是禁止控制角色。第4课第53页将具体API/应用服务/仓储放到后续OOD；第5课再以一个用例做局部协作，二者是阶段递进。

| 用例位置 | 责任承担者 | 需要守住的规则 |
| --- | --- | --- |
| 接收文本、角色与上下文并返回结果 | 边界职责 | 请求结构、角色作用域及错误说明；不能把客户端声明当真实权限 |
| 组织意图识别、能力检查、建议生成与执行回执关联 | 控制职责 | 保留标识，协调超时、拒绝及有效期，不把建议当完成 |
| 保存指令含义、有效期与状态，按合法阶段接受反馈 | 指令/回执等领域对象职责 | 过期拒绝、状态合法、回执关联原指令 |
