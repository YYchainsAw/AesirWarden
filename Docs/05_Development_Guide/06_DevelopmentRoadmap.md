# 当前开发计划

目标顺序沿用 2026-10-07 确定的计划：**先完成 BT 的完整游玩流程，再以 RL Boss 为重点，继续完善玩家与 AI 队友，最后整合展示。**

任务状态统一查看 [UE 开发视图](https://github.com/users/YYchainsAw/projects/2/views/3)或[两仓总看板](https://github.com/users/YYchainsAw/projects/2/views/2)。任务详情、依赖、负责人和完成情况在 GitHub 维护，本页不另存一份清单。

## 现在先做 M1：把游戏完整玩一遍

已有玩家移动、攻击、翻滚和可战斗的 BT Boss；接下来把这些部件连接起来。这个基础来自已有开发记录，实际接线情况以打开当前地图后的检查为准。

| 顺序 | 完成后的样子 | 开发入口 |
| --- | --- | --- |
| 1 | 打开游戏看到菜单，开始后交还玩家相机、输入和 HUD | [流程接线](05_LevelFlowGuide.md) |
| 2 | 从关卡起点走到 Boss，入场结束后才启动战斗 | [第一关流程](../02_Design_Doc/GDD/01_GameFlow.md) |

## 后续目标继续保留

| 阶段 | 要做到什么 | 关键完成条件 |
| --- | --- | --- |
| M1 · 完整流程 | BT Boss 版本从开始玩到结算、重试、返回 | PIE 和 Windows 包都能走通 |
| M2 · RL 实战 | 完善 Boss 动作，让冻结 PPO 通过同一 GAS 执行器完成战斗 | 两端规则一致，真实模型响应，故障能回退 BT，重试无上一局残留 |
| M3 · RL 对照 | 说明 PPO 与 BT 的实际差异和限制 | 独立测试与 UE 同条件对照有原始数据、版本和可复现分析 |
| M4 · 玩家完善 | 完善数值、技能、输入衔接和反馈 | 先确定技能及数值范围，再实现、调手感和回归 |
| M5 · AI 队友 | 在游戏里聊天、响应约定指令并参与战斗 | 服务样例能在 UE 执行，成功或失败有回执，故障和重试可处理 |
| M6 · 综合展示 | 在同一明确版本演示选定功能 | 启动说明、资产、模型、打包、素材来源和演示记录齐全 |

M2 是 M1 之后的重点。M4/M5 可以按实际依赖并行准备，具体技能数量、训练预算和工期尚待确定。

UE 侧全部由自己开发；自己也负责 Python Boss RL。队友负责 Python NPC 服务。NPC 的人格包、跨游戏接入与外部包校验扩展继续由服务侧推进，不作为 M1/M2 的前置条件。

## 推进时的约定

2026-10-21采纳的[AI部署目标](../02_Design_Doc/TDD/06_Deployment.md)纳入M2/M5/M6的交付：M2验证本地Boss与模型身份，M5完成远程NPC隔离/同步/ASR及本地执行，M6验证正式Windows包、离线与发布回滚。方向不改变M1先完成BT全流程的顺序，不把目标采纳写成已部署或已通过。

同日采纳的[NPC交互与服务演进](../02_Design_Doc/TDD/07_NPCInteractionEvolution.md)以EVO-20261021单列20项，纳入M5与适用的M6检查：先完成请求/旧局失效、真实执行和持久幂等/身份，再接事件治理、追踪与按键外部ASR，随后完善来源记忆/重置同步，最后推进VAD、TTS/打断及按需检索评估。基础语音输入可并行准备，后置语音输出不阻塞M1/M2或M5最小输入闭环；任务状态仍只在看板维护。

- BT 基础流程不等待 RL 模型或 NPC 服务；PPO 与故障回退在 M2 检查。
- 玩家技能、数值和队友接入都是已确定的目标；[技能与成长页](../02_Design_Doc/GDD/05_MagicSystem.md)中的具体草案需要另行确认后再实施。
- 正式 BT–PPO 对照保持单玩家对单 Boss、同一执行规则。技能、伤害、时序或性能发生变化时，保留研究版本或重测受影响条件。
- 日常按[检查表](../06_Test_Doc/01_VerificationMatrix.md)确认功能；正式实验按[评估方案](../08_RL_Research/03_EvaluationProtocol.md)记录版本和条件。
- 发现缺陷先复现，在已有 Issue 或[已知问题](../06_Test_Doc/02_KnownIssues.md)记录，避免把一次静态猜测直接当作已复现 Bug。
